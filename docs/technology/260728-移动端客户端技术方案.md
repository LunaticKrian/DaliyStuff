## 1. Context（背景与目标）

PixelPack 已是标准 CS 架构：Vue 3 SPA（`web/`）↔ FastAPI 服务端，经 `airise-gateway` 终结 TLS 反代挂在 `*.airise.site`；桌面端已落地为 **Tauri 2 瘦客户端**（`application/desktop/`）。本次新增**移动端原生 App**（iOS/Android），让用户在手机拥有「常驻可达、原生通知、生物识别应用锁、相机/分享集成」的原生体验。

桌面端技术方案当时即明确「桌面先行，移动在后…选型须为移动端留路」——移动端是计划内的延伸，**与桌面端共用同一世界观与前端基座**。

### 核心需求（已与产品确认）

1. **瘦客户端**：所有数据接口与后端服务**仍在线上服务器**（`api` 容器不变，服务端零改动）。移动端只做 UI + 调 API + 原生能力。
2. **双平台**：iOS + Android 同时覆盖。
3. **原生能力**：系统通知 / 推送、相机（拍照加物品）、系统分享、**应用锁（PIN + 生物识别）**、断网只读缓存。
4. **数据模式**：在线为主 + 轻量只读缓存——服务器是唯一数据源，移动端仅缓存最近响应应用于提速与断网只读，**不本地写入、不双向同步**。
5. **UI**：**全新移动端设计**（非响应式套壳）——底部 Tab Dock + Hub 模式，移动端原生交互（手势、底部抽屉、FAB）。
6. **范围**：完整对齐 Web 全部模块。

## 2. 选型结论

**选 Tauri 2 mobile。** 桌面端已是 Tauri 2 + 复用 `web/`，移动端同栈 → **最大化复用、最小化认知与维护成本、世界观一致**。Tauri 2 原生支持 iOS（WKWebView）/ Android（System WebView），同一 Rust shell、同一 `web/dist`、同一套平台层（`platform.ts` / `client.ts` / `auth` / `sse` / `refresh.ts`）。

| 方案 | 结论 | 理由 |
|---|---|---|
| **Tauri 2 mobile** ✅ | 采用 | 与桌面端统一；复用 `web/` SPA + 平台层 + keyring 命令模式；Rust 原生能力（安全存储/生物识别）一处实现两端复用 |
| Capacitor | 否决 | 移动生态更成熟，但会与桌面端形成**两套壳**；桌面端已沉淀的 Rust keyring/命令需用 JS 插件重做，重复劳动 |
| React Native / Flutter | 否决 | 原生组件重写 UI，像素/CRT 主题需整套重制、与 `web/` 维护双份代码，工期与长期成本最高 |

> ⚠️ Tauri 2 mobile 生态相对较新，部分桌面插件（keyring / 推送 / 相机）的**移动端支持需在实现期逐个验证**（见 §6 风险），必要时用平台原生或社区插件替代。

## 3. 总体架构

```
┌───────────────────────────── 移动设备 ─────────────────────────────┐
│  Tauri 2 Rust 外壳（application/mobile/src-tauri/）                 │
│   ├ 安全存储：iOS Keychain / Android Keystore（存 refresh token）   │
│   ├ 生物识别 / 推送 / 相机 / 分享（插件，按需）                       │
│   └ WebView 加载 web/dist（Vue SPA，移动端视图层）                   │
│         ├ 复用：api/* · stores/* · composables/* · types/* · sse    │
│         └ 移动端独立视图：views/mobile/* + layouts/MobileLayout.vue │
└──────────────────────────────────┼──────────────────────────────────┘
                                   │ HTTPS（api.airise.site，经 airise-gateway）
                                   ▼
                   线上 FastAPI（api 容器，零改动）
```

### 3.1 前端：路由分流 + 移动端独立视图层（共享业务逻辑）

因选「全新移动端设计」，**不走纯响应式断点**，而是：

- **共享**：`api/*`、`stores/*`、`composables/*`、`types/*`、`utils/sse.ts`、`utils/refresh.ts`、`utils/exportPdf.ts`、设计 token（`--pixel-*`）——业务逻辑与数据层一处维护。
- **分流**：`router/index.ts` 按 `platform.isMobile` 将同一逻辑路由指向 `views/mobile/*`（移动版）或现有 `views/*`（桌面/Web 版）。
- **移动外壳**：`layouts/MobileLayout.vue` = 设备状态条 + 屏幕 viewport + Tab Dock（对应设计稿 `.statusbar` / `.viewport` / `.tabbar`）。

> 即「业务逻辑共享、视图分叉」。移动端拿到全新交互，但 API 调用、鉴权、SSE、PDF 导出等全部复用，无重复实现。

### 3.2 鉴权与设备会话（复用 260727 会话化成果）

- 移动端 = 又一台**设备会话**，复用已落地的 refresh 轮换 + 会话级复用检测 + `/sessions` 设备管理。
- refresh token 存**安全存储**（Keychain/Keystore），复用桌面端 `commands.rs` 的 keyring 命令模式（移动端适配）。
- 前端复用统一 `utils/refresh.ts` worker（260727 已收敛 client/sse/auth 三路），移动端无需另造。
- **应用锁（PIN + 生物识别）**：落地 260727 规划的 GUILD LOCK——启动/回到前台时校验；PIN 必备，生物识别快捷。

### 3.3 数据流

所有模块（物品/任务/智核/世界地图/履历/日志/统计/传输）数据流与 Web 端**完全一致**，仅视图层不同：

- 普通接口：`api/client.ts`（JWT 注入 + 401 自动 refresh）。
- 流式：智核对话 / 任务生成 / 世界地图侦测走 `utils/sse.ts`（fetch ReadableStream，移动 WebView 支持）。
- 传输：WebRTC P2P（复用 `260718-点对点数据传输.md` 方案，移动端需评估 ICE/STUN 在移动网络下的表现）。
- 履历 PDF：复用 `utils/exportPdf.ts`（html2pdf）；移动端导出后走系统分享/保存。

## 4. 关键约束与前置条件

1. **构建环境**：
   - iOS：macOS + Xcode + Apple Developer 账号（签名分发）。
   - Android：Android Studio + JDK + 签名 keystore。
   - Rust：`rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios aarch64-linux-android armv7-linux-androideabi x86_64-linux-android i686-linux-android`。
   - Tauri 2 CLI（`application/mobile/` 装 `@tauri-apps/cli`）。
2. **WebView**：iOS WKWebView（系统自带，OK）；Android System WebView（Android 5.0+，现代设备 OK）。
3. **服务端零改动前提**：CORS 已 `*`（见 README），鉴权会话化已支持多设备会话——移动端接入即「新设备」。
4. **网络**：在线为主；弱网/断网靠轻量只读缓存兜底（P1）。
5. **CSP**：`tauri.conf.json` 的 CSP 保留 `connect-src 'self' https: wss:`，覆盖线上 API + WS。
6. **应用锁安全上下文**：生物识别依赖平台安全上下文，越狱/Root 设备降级为仅 PIN。

## 6. 风险与偏离（实现期跟踪）

1. **Tauri 2 mobile 插件支持**：keyring / 推送 / 相机 / 生物识别的移动端插件需逐个验证；缺失则用平台原生或社区插件替代——**任何替代须回写本方案**。
2. **Rust 侧未本机验证**：本机环境暂未装 Rust（同桌面端），首次 `cargo`/`tauri ios`/`tauri android` 构建需先备齐工具链。
3. **WebRTC on mobile**：移动网络下 ICE/STUN 候选与 NAT 穿透表现需实测（参考桌面端 trick-ICE 经验）。
4. **PDF 导出**：html2pdf 在移动 WebView 下的字体子集/渲染需回归（260726 字体改动连带）。
5. **全新移动视图层工作量**：~16 视图，建议分期（见 §7）。

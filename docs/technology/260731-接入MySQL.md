## 0. 已定决策（与用户确认）

| 维度 | 决策 |
|---|---|
| 数据库 | **MySQL** 替换现有 SQLite（自然升级路径：同方言家族、宽松类型、生态最厚） |
| 部署形态 | **docker-compose 内置 `mysql:8.4`（LTS）容器**，单节点，全栈自包含 |
| Python 驱动 | **`asyncmy`**（应用运行期，SQLAlchemy 2.0 async） |
| Schema 迁移机制 | **引入 Alembic**（依赖已在 requirements，本次正式接入），废弃 `create_all` + `PRAGMA ensure_column` |
| Alembic 运行驱动 | **`pymysql`（sync）** 跑迁移；运行期仍 asyncmy（见 §3） |
| 现有数据 | **迁移**：一次性 ETL 把 `server/data.db`（344KB / 24 表 / ~365 行 / 13 用户）导入新库 |
| 测试库 | **换 MySQL**：测试连独立 `pixelpack_test` 库，消除 SQLite/MySQL 方言漂移 |

## 1. 背景与问题

当前持久化层（`server/app/`）：

- **驱动 / URL**：`aiosqlite`，`DATABASE_URL = "sqlite+aiosqlite:///./data.db"`（`config.py:5`、`docker-compose.yml` 注入 `sqlite+aiosqlite:////app/data/data.db`）。
- **建表机制**：**未启用 Alembic**（`alembic` 在 requirements 里但从未接入）。启动时 `Base.metadata.create_all` + 一个自定义 `ensure_column()`（`utils/migrate.py`，基于 SQLite `PRAGMA table_info`）在 `main.py` lifespan 里手工补列。
- **裸 SQL**：真正的 `text()` 裸 SQL 全项目仅 **2 处** —— `main.py` 的 `UPDATE ... date(published_at)`（SQLite `date()` 清洗脏数据）、`migrate.py` 的 `PRAGMA table_info`。
- **ORM**：SQLAlchemy 2.0 async，`Mapped`/`mapped_column`，全用**通用类型**（`Integer/String(N)/Text/DateTime/Date/Boolean/JSON`）。模型层零 SQLite 专用写法；**无** `on_conflict`/`RETURNING`/`AUTOINCREMENT`/`ROWID`。
- **FK**：少量 `ForeignKey(ondelete="CASCADE")`（image / resume / cost / item 的关联表）。

**问题**：SQLite 是单文件嵌入式库，不适合现网多连接 / 备份 / 运维 / 横向扩展；手工 `ensure_column` 不可审计、不可回滚；测试与生产同库同文件易串。迁到 MySQL 后，借机把 schema 纳入版本化迁移。

**关键判断：本次是低风险迁移。** ORM 抽象干净，模型层几乎零改动，真正要换的只有「驱动 + URL + 2 处裸 SQL + 建表机制 + 部署编排」。

## 2. 目标与非目标

**目标**
1. 应用持久化层从 SQLite 切到 MySQL，运行期 async。
2. schema 纳入 Alembic 版本化迁移，废弃 `create_all` + `PRAGMA` 自举。
3. 现有 `data.db` 数据无损迁入新库（保留主键 / FK 关系）。
4. 测试改连 MySQL，与生产同方言。
5. docker-compose 全栈自包含（含 mysql 容器），`docker compose up` 即起。

**非目标**
- 不做主从 / 读写分离 / 分库分表（单节点足够当前量级）。
- 不改任何业务逻辑、不改 API、不改前端。
- 未来如需分布式 / 强 HA，再评估 OceanBase / TiDB 等方案。

## 3. 选型结论

### 3.1 为什么 MySQL（而非 PostgreSQL / OceanBase）
- ✅ **SQLite 的自然升级路径**：同 SQL 方言家族、同样宽松类型，迁移摩擦最小；当前 ORM 用通用类型，几乎零改动即可落到 MySQL。
- ✅ **生态最厚**：所有 ORM / 驱动 / 备份 / 监控工具一等支持；中文社区与 Stack Overflow 覆盖最全。
- ✅ **轻量**：官方镜像 ~150MB、秒级冷启动、单节点 ~150–300MB 内存。
- ❌ 否决 PostgreSQL：功能更强（JSONB / 全文检索 / GIS），但 SQL 最严格（SQLite 宽松类型迁过去要适应）、且当前无 PG 独有需求（搜索 / GIS / 复杂分析）。若未来有这类需求再评估。
- ❌ 否决 OceanBase：分布式 / HTAP / 金融级 HA 的价值在当前量级（13 用户、344KB、单机）激活不了，反要背 ~2GB 内存 + 1~2 分钟冷启动 + 更重运维；MySQL 兼容也只是「高度」非「完全」。规模到了再上 OB，代码层无伤（仍是 MySQL 协议）。

### 3.2 为什么 compose 内置 `mysql:8.4` 容器
- ✅ 全栈自包含，`docker compose up` 即起，零外部依赖。
- ✅ 官方镜像能力齐全，**比自建 OB 方案大幅简化**：
  - `MYSQL_DATABASE=pixelpack` → 首启自动建库，**不需要 db-init 服务**；
  - 镜像自带 `mysqladmin` → healthcheck **无客户端不确定性**；
  - 数据目录 `/var/lib/mysql` 尽人皆知；
  - 秒级冷启动、~150–300MB 内存。
- ❌ 否决托管 RDS / 云 MySQL：本地开发与自部署无需云依赖，未来可平滑切（只改 `DATABASE_URL`）。

### 3.3 为什么 asyncmy
- ✅ Cython 实现，吞吐显著高于 aiomysql；SQLAlchemy 2.0 async 一等支持。
- ❌ 否决 aiomysql：纯 Python 易编译，但慢、维护偏保守。
- **代价**：C 扩展，镜像构建需关注 wheel 命中 / 构建依赖（见 §5.6）。

### 3.4 为什么 Alembic
- ✅ 迁到真 RDBMS 后，`PRAGMA ensure_column` 是 SQLite 专用、不可回滚、不可审计；Alembic 给版本化、可 review、可 downgrade 的迁移，依赖早已在 requirements。
- ❌ 否决「仅把 ensure_column 改写成 information_schema」：治标，仍无迁移历史。

### 3.5 为什么 pymysql 跑 Alembic（而非 async env.py）
- ✅ 迁移无需 async；sync env.py 最简、最稳；pymysql 纯 Python 零编译。
- 运行期仍是 asyncmy，互不干扰。同一 `DATABASE_URL` 派生 sync 变体（见 §5.3）。

### 3.6 为什么测试也换 MySQL
- ❌ 否决「测试保留 sqlite 求快」：SQLite 弱类型、布尔存 0/1、JSON 存 TEXT、无真 FK 约束 —— 与生产 MySQL 方言漂移，单测过但生产炸（典型坑）。
- ✅ 换 `pixelpack_test` 库，与生产同方言。代价：建表略慢，当前测试量级可接受。

## 4. 架构与数据流

```
docker-compose
├── mysql   mysql:8.4 (LTS, 端口 3306, 卷 ./data/mysql)
│           MYSQL_DATABASE=pixelpack → 首启自动建库 + 建 app 用户
├── api     depends_on: mysql(healthy) → entrypoint: alembic upgrade head → uvicorn
│           DATABASE_URL = mysql+asyncmy://pixelpack:***@mysql:3306/pixelpack?charset=utf8mb4
└── web     静态前端（不变）
```

- **连接拓扑**：`api` 走 compose 内网 `mysql:3306`；3306 默认不暴露宿主（仅调试时映射）。
- **数据流不变**：API ↔ ORM (SQLAlchemy async) ↔ asyncmy ↔ MySQL ↔ InnoDB。业务代码无感。
- **schema 落地**：由 `api` 容器 entrypoint 跑 `alembic upgrade head`，应用启动即对齐 schema。

## 5. 改动清单（文件级）

### 5.1 依赖 — `server/requirements.txt`
```diff
- aiosqlite
  sqlalchemy[asyncio]
  alembic
+ asyncmy              # 应用运行期 async MySQL 驱动
+ pymysql              # Alembic 迁移用（sync）；纯 Python，零编译
```

### 5.2 配置与引擎 — `server/app/config.py` + `app/database.py`
`config.py` 默认 URL 改为本地 MySQL：
```python
DATABASE_URL: str = "mysql+asyncmy://pixelpack:pixelpack@127.0.0.1:3306/pixelpack?charset=utf8mb4"
```
`database.py` 引擎加 MySQL 连接池参数（MySQL 会清空闲连接，`pool_pre_ping` 防 "server has gone away"）：
```python
engine = create_async_engine(
    settings.DATABASE_URL,
    pool_size=10,
    max_overflow=20,
    pool_recycle=1800,     # < MySQL wait_timeout（默认 28800，保守取短）
    pool_pre_ping=True,    # 取连接前 ping
    pool_timeout=30,
    echo=False,
)
```
`get_db()` / `Base` 不变。

### 5.3 Alembic 接入
- `server/` 下 `alembic init alembic`（同步模板）。
- `alembic/env.py` 关键改动：
  ```python
  from app.config import settings
  from app.database import Base
  import app.models  # 触发所有模型注册到 Base.metadata（同 main.py 的导入效果）

  # 运行期是 asyncmy，迁移用 sync pymysql —— 从同一 URL 派生
  sync_url = settings.DATABASE_URL.replace("+asyncmy", "+pymysql")
  config.set_main_option("sqlalchemy.url", sync_url)
  target_metadata = Base.metadata
  ```
- 初始迁移（**在空库上** autogenerate，一次性覆盖全部 24 张表 + 关联表）：
  ```bash
  DATABASE_URL='mysql+asyncmy://pixelpack:pixelpack@127.0.0.1:3306/pixelpack?charset=utf8mb4' \
    alembic revision --autogenerate -m "init schema"
  ```
  ⚠️ **必须人工 review 生成结果**（autogenerate 在干净库上通常完整，但确认列类型 / `server_default` / 索引 / FK 与模型一致）。
- 历史的 `ensure_column`（`exp` / `is_admin` / `disabled` / `must_change_password` / `intel_articles.user_id` / `resumes.template` / `resume_pending_changes.lang`）**全部已被初始迁移覆盖**（fresh schema 本就含这些列），无需再补。

### 5.4 删除 SQLite 专用代码 — `server/app/main.py` + `utils/migrate.py`
- `main.py` lifespan：
  - 删 `await conn.run_sync(Base.metadata.create_all)` 与所有 `ensure_column(...)` 调用 —— 改由 entrypoint 的 `alembic upgrade head` 负责。
  - 删 `UPDATE intel_articles SET published_at = date(...)` 清洗（脏数据在 ETL 时归一化，新库不再需要）。
  - **保留** `ensure_superadmin()`（数据 seed，在迁移之后执行）与 intel 调度器（不动）。
- `utils/migrate.py`：整文件删除（`ensure_column` 不再被引用）。

### 5.5 docker-compose — 新增 `mysql`，改 `api`
```yaml
  mysql:
    image: mysql:8.4                    # LTS；生产固定 tag，勿用 latest
    container_name: pixelpack-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:-pixelpack}
      MYSQL_DATABASE: pixelpack         # 首启自动建库 → 不需要 db-init
      MYSQL_USER: pixelpack             # 自动建 app 用户并授予 pixelpack 全权限
      MYSQL_PASSWORD: ${MYSQL_APP_PASSWORD:-pixelpack}
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_unicode_ci
    volumes:
      - ./data/mysql:/var/lib/mysql:Z   # 持久化到宿主；:Z 给 SELinux(CentOS 部署)打标签，Mac/Docker Desktop 下 no-op
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p$$MYSQL_ROOT_PASSWORD --silent"]
      interval: 5s
      timeout: 5s
      retries: 20
      start_period: 30s
    networks: [airise-web]

  api:
    # ... 原有 ...
    depends_on:
      mysql: { condition: service_healthy }
    environment:
      DATABASE_URL: "mysql+asyncmy://pixelpack:${MYSQL_APP_PASSWORD:-pixelpack}@mysql:3306/pixelpack?charset=utf8mb4"
      UPLOAD_DIR: "/app/data/uploads"
    volumes:
      - ./data/uploads:/app/data/uploads   # ⚠️ 不再挂 data.db；MySQL 数据在 mysql 服务的 ./data/mysql 卷
    networks: [airise-web]
```
> `web` 服务不变（仍只读挂 `./data/uploads`）。
> 首启由 `MYSQL_DATABASE` 自动建库；之后容器重启不会重复建（数据在卷里）。

### 5.6 Dockerfile — asyncmy 构建 + entrypoint
- **构建依赖**（已验证）：asyncmy 是纯 Cython —— **amd64 有 manylinux wheel 直接用；arm64（Apple Silicon 本机构建）无 wheel，需源码编译**，只要 `gcc` + libc 头文件（`stdlib.h`，来自 `libc6-dev`），**不需要 MySQL 客户端头文件**。用 `build-essential` 一次装齐，pip 后同层 purge，不增镜像体积：
  ```dockerfile
  RUN apt-get update \
   && apt-get install -y --no-install-recommends build-essential \
   && pip install --no-cache-dir -r requirements.txt \
   && apt-get purge -y --auto-remove build-essential \
   && rm -rf /var/lib/apt/lists/*
  ```
  （生产在 amd64 服务器原生构建命中 wheel 不触发编译；该层对 amd64 无害、对 arm64 dev 必需，保留以健壮跨平台。）
- **entrypoint 跑迁移**：新增 `server/entrypoint.sh`，`CMD` 改为调用它：
  ```sh
  #!/bin/sh
  set -e
  alembic upgrade head
  exec uvicorn app.main:app --host 0.0.0.0 --port 8000 \
       --log-config app/uvicorn_log_config.json
  ```
  ```dockerfile
  COPY entrypoint.sh .
  RUN chmod +x entrypoint.sh
  CMD ["./entrypoint.sh"]
  ```

## 6. 数据迁移（一次性 ETL）

新增 `server/scripts/migrate_sqlite_to_mysql.py`，**仅在切换首次运行**：

- **源**：`sqlite3`（stdlib，只读连 `data.db`）。
- **目标**：SQLAlchemy sync 引擎（pymysql）连 `pixelpack`（迁移已跑完、schema 已建）。
- **表顺序**：用 `Base.metadata.sorted_tables`（拓扑序，满足 FK 依赖）。
- **逐表** `SELECT *` → 类型映射 → bulk insert：
  | SQLite 存储 | 目标列 | 处理 |
  |---|---|---|
  | INTEGER (PK) | INT | 显式插 `id`，保留原值（维护 FK 关系）；AUTO_INCREMENT 自动跟上 max(id) |
  | INTEGER (0/1) | BOOLEAN / tinyint | 原样 int |
  | TEXT (JSON) | JSON | `json.loads` → 传 dict，SQLAlchemy 序列化回 |
  | TEXT (datetime) | DATETIME | `datetime.fromisoformat` |
  | TEXT (date，含脏数据) | DATE | 取前 10 位 `'YYYY-MM-DD'`（等价旧 `date()` 清洗） |
- **幂等**：目标表非空则跳过该表；或用 MySQL `INSERT ... ON DUPLICATE KEY UPDATE`。
- **FK**：批量装载数据期间 `SET FOREIGN_KEY_CHECKS=0`，完成后 `1`。
- **校验**：逐表对比 `COUNT(*)` 源 vs 目标；抽样关键表（users / resumes / resume_chat_threads）行数。

## 7. 关键约束与前置条件

| 项 | 要求 |
|---|---|
| MySQL 版本 | **8.4 LTS**（或 8.0）；InnoDB 引擎 |
| 字符集 / 排序 | 库 / 连接 / 表均 **utf8mb4** + `utf8mb4_unicode_ci`（中文内容 + emoji） |
| 认证插件 | 默认 `caching_sha2_password`（asyncmy 新版支持）；若命中老版 asyncmy 报认证错，给 app 用户改 `mysql_native_password` |
| 冷启动 | **秒级**（~10–20s），`api` 经 healthcheck `service_healthy` 等待即可 |
| 内存 | 单节点 ~150–300MB（远低于 OB 的 ~2GB） |
| 持久化 / 权限 | bind mount `./data/mysql:/var/lib/mysql:Z`。镜像 entrypoint 以 root 启动、首启自动 `chown` 给 mysql 用户(UID 999)，空目录无需手动 chown；`:Z` 处理 CentOS/SELinux 标签；`down`/`down -v`/重建镜像均不丢宿主目录数据 |
| asyncmy 构建 | amd64 走 wheel；arm64 需 `build-essential` 编译 Cython 扩展（已实现，§5.6），无 MySQL 头文件依赖 |
| JSON/TEXT 列默认值 | MySQL **不允许** JSON/TEXT/BLOB 列字面 `DEFAULT`（报错 1101）。需表达式形式：JSON 列 `server_default=text("('{}')")`、TEXT 列 `text("('')")`（已修 `users.settings` / `audit_logs.detail` / `intel.body`） |
| SQLite 日期函数 | MySQL 无 `strftime` / `date` / `datetime` / `julianday`（报错 1305 FUNCTION 不存在）。`func.strftime("%Y-%m", col)` → `func.date_format(col, "%Y-%m")`，**参数顺序反转**；「当前时间」`func.strftime(fmt,"now")` → `func.date_format(func.now(), fmt)`（已修 `admin.py` / `llm_config.py` 的当月用量比较） |
| 网络安全上下文 | 无新增（3306 仅 compose 内网可达，默认不暴露宿主） |

## 8. 风险与回滚

| 风险 | 缓解 |
|---|---|
| asyncmy 无 wheel、slim 镜像编译失败 | §5.6 补 build deps；最坏退驱动为 aiomysql（纯 Python，仅改 URL `+asyncmy`→`+aiomysql`） |
| 认证插件不兼容（caching_sha2） | §7：改 app 用户为 `mysql_native_password` |
| Alembic autogenerate 漏列 / 类型偏差 | 人工 review 初始迁移；DoD 用 `create_all` 对照核 |
| 测试 `create_all` 与 alembic 漂移 | §5.7 维护约束；后续测试改跑 `alembic upgrade head` |
| ETL 类型 / FK 错乱 | §6 计数校验 + 抽样；失败可重跑（幂等） |
| 切换中断 / 数据不一致 | 保留 `data.db` 原文件不删；切换窗口内停写；失败回滚 = 把 `DATABASE_URL` 改回 sqlite |

**回滚策略**：旧 `data.db` 文件保留；切换期间 `DATABASE_URL` 是唯一开关，回滚即改回 `sqlite+aiosqlite`（回退到上一个 git tag，或临时保留 SQLite 兼容代码到验证通过后再清）。
